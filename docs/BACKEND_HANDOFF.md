## Mandatory guidance for future Claude sessions

1. **Read before you build.** Before any backend-dependent work — API operations, request/response models, errors, auth/session, registration, profile, legal documents and Terms, account deletion, moderation, support tickets and photos, chat, notifications, push, Firebase, Sentry, quizzes, flashcards, points, levels, badges, daily tasks, entitlements, staging tests, production configuration, App Store or Google Play submission — read the relevant section of this file **and** the contract section and decision record it points to. Use the lookup table below to jump.
2. **Check the version before you rely on a version-specific fact.** Read `contract/SOURCE.md` and `info.version` in `contract/openapi.yaml` (the pin), then check what the backend actually serves (BH-B3). Anything tagged `[3.47]` or `[3.48-DRAFT]` is **not in the pin**. Features Seif describes as new in `3.47.0-m1` must not be assumed available to the app unless the pinned `openapi.yaml` says `3.47.0-m1` (or the owner has explicitly authorised building ahead of the pin, as was done for `name_not_allowed`). Do not assume the baseline or the planned versions in this file are still current — revalidate.
3. **Order of authority.** The pinned contract (`stable` operations only) and current verified server behaviour are the technical references. Seif's message is authoritative for the facts he explicitly confirmed, **with its date (2026-10-09) and its version caveats preserved**. A statement by Seif never creates an endpoint, field or error code that the contract does not have.
4. **Planned is not live.** Never turn planned work into a claim that an endpoint, deployment, Firebase project, push service, reviewer account or production feature is live. An intended date is not evidence of a deployment. Say `PLANNED` until a dated probe says otherwise, and record the probe.
5. **Never invent.** No endpoint paths, response fields, error codes, retention policies, legal text, reviewer credentials, supported-product behaviour, or EN/AR copy that is not written down here or in the contract. Approved wording is quoted verbatim with its approval status; unapproved wording stays out of app resources (owner's provisional-copy rule).
6. **Do not re-ask answered questions.** If a row here, the contract or a decision answers it, use it. §L1 lists every Seif question and where it is answered. Re-ask only when evidence shows the answer is incomplete, contradictory, outdated or no longer applicable — and say which.
7. **Ask only the residual.** For a genuinely new backend question: check this file, the contract, `docs/DECISIONS.md`, `docs/seif_fight.md` and the code first; then file only the remaining specific uncertainty in `docs/seif_fight.md` (the repo's standing route). Numbering: `SQ-n` ids belong to the draft message `.ai/audits/current/completion/02_SEIF_HANDOFF.md`; `S-n` ids are the standing register `docs/seif_fight.md`. A new residual gets the next free `S-n` plus one row in §L2; the owner folds it into the next message to Seif. **Do not send messages, or write to any external system, on the owner's behalf.** Read-only probes (a `GET`, `git ls-remote`, a DNS lookup) are allowed when the task needs them and the owner has not forbidden network access; a registration, a ticket, a quiz or any other write to staging, an app registration, or a message to a person needs the owner's explicit word.
8. **Owner-controlled decisions need explicit authorisation:** the contract pin / any re-vendor, environment identities, application ids, Firebase / Apple / Google registrations, production configuration, store accounts, release scope, user-facing copy. Seif's reply does not authorise any of them.
9. **Keep four things apart:** backend facts (Seif / contract), product decisions (owner / `DECISIONS.md`), implementation notes (repo state), unresolved questions (§L2). Do not blend them in one sentence.
10. **When a fact changes, record it.** Update the row, keep the old value with its date ("was … until …"), add a line to the Change log with source and date. Never replace silently. Archive any new written message from Seif verbatim under `docs/` (as `SEIF_REPLY_<date>.md`, with its sha256) and cite the copy — the two 2026-10-07 messages exist only in `Downloads` and are **not** archived (a known gap).
11. **Reference, do not paste.** A wave brief or task plan cites the rows it depends on by id (for example `BH-C5`, `BH-G9`) instead of copying this file.
12. **Conflicts stop work.** If two sources disagree (contract edition vs Seif vs repo), stop and report the exact conflict: file paths, versions, evidence. §K lists the ones already known.
13. **Secrets stay out.** Never write a production or reviewer code, token, DSN, server key or a real person's phone number here or anywhere in the repo. The contract-published staging test code and the reserved `+20100000000xx` numbers are not secrets, but this file does not repeat the code: cite the contract paragraph; a test harness may use it. This file points to where authoritative instructions live (for staging sign-in, the OTP notes in `contract/openapi.yaml`'s top-level description).
