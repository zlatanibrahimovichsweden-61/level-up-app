# API contract changelog (partner-facing)

Every change to `openapi.yaml`, `error-codes.md`, or `realtime.md` gets a dated entry: **what changed, why, who's affected, breaking? (yes / no / BEHAVIOURAL)**. The Flutter partner watches this file; changes are announced at or before the weekly sync (Interfaces doc §1.5). Newest first.

> **`Breaking: BEHAVIOURAL` (adr-038)** — a third category, added 2026-08-11. The schema did not break (your build will succeed, your generated models are still correct) but the **meaning moved**: an endpoint returns a different set, or returns under different conditions, than it did before. **These are the dangerous ones** — a real break announces itself in your build output, a behavioural change never does. They are announced as loudly as a break and need the same acknowledgment. In `openapi.yaml` the affected operations carry `x-behaviour-changed: <version>`.

- 2026-08-16 — **`POST /auth/recovery/new-phone` declares the `400 validation_failed` it has always returned**. `info.version` bumped `2.0.0-m1` → **`2.1.0-m1`**. **Breaking: no** — purely additive, and explicitly **NOT `BEHAVIOURAL`**: the server's behaviour is byte-for-byte what it was. **Nothing to do** unless you are building the recovery ladder, which is still `draft` and still not safe to build against.
  - **What changed.** One response added to one `x-stability: draft` operation: `400` + `validation_failed` when `newPhone` is missing or is not a valid E.164 number. No path, schema, field, requiredness, error code or `x-stability` value moved. `error-codes.md` and `realtime.md`: **unchanged** — `validation_failed` has been registered since the first contract.
  - **Why it was missing, and why the fix is a contract change rather than a code change.** `newPhone` is a `$ref: Phone` whose pattern the client is expected to enforce, so the operation was written as if a malformed value could not arrive. It can. The server has always answered `400 validation_failed`, because the two alternatives are both believable lies: `registration_token_invalid` would tell a student their still-valid rebind token is dead and cost them two proven recovery rungs, and `phone_already_registered` would claim the number belongs to someone else. The contract understated reality; it now matches.
  - **How it was found: Schemathesis, from outside, against a running server.** CI now fuzzes the `/auth/*` surface against this document and fails the build on any status a response returns that the contract does not declare (spec-002 group 11). It flagged this operation along with three others. **This is the gate working as intended** — the divergence had been known and written down in a code comment for a day, and the external check is what turned a comment into a change.
  - **The other three were fixed the opposite way, and the distinction is worth knowing.** `POST /auth/refresh` and `POST /auth/recovery/start` also emitted an undocumented `400` for a structurally malformed body (a JSON object where a string is declared, a non-object root, unparseable JSON, a missing `Content-Type`). On those two the absence of a `400` is a deliberate **security property**, not an omission — a field-level `400` tells an unauthenticated caller which half of a credential it got wrong, and on `recovery/start` it breaks the guarantee that a malformed number, an unknown number and an ineligible account are indistinguishable. So there the contract was right and the **code** was corrected: every unusable body now reaches the handler as an absent value and gets the published `401` / `404`. **No contract change on those two, and none is coming — do not code a `400` branch for `/auth/refresh` or `/auth/recovery/start`.**
  - Breaking: **no.**
- 2026-08-16 — **`POST /auth/register` gains the REQUIRED `device` object on both track bodies (adr-019 device binding)**. `info.version` bumped `1.3.0-m1` → **`2.0.0-m1`**. **Breaking: YES.** This is the first genuinely breaking change this contract has ever shipped, and it is announced as such even though its practical impact is believed to be zero — see "who is actually affected".
  - **What changed.** `SchoolRegistration` and `UniversityRegistration` each gain `device` (`DeviceInfo`, the same shape already used by `POST /auth/otp/verify` and `POST /auth/recovery/confirm`) and each adds `device` to its `required` list. **Nothing else moved** — no other field, no response, no error code, no `x-stability` value, and no other operation.
  - **Why it is breaking, stated plainly.** Adding a REQUIRED request field invalidates any previously-valid body. A client that compiled against `1.3.0-m1` and sends a registration without `device` now gets `400 validation_failed`.
  - **Who is actually affected: nobody, and that is why now.** `POST /auth/register` was **not implemented until 2026-08-15** — it returned `404` on staging until that day. No client can have successfully registered against it, so there is no working integration for this to break. **This is the cheapest moment this change will ever have**, and it gets more expensive the moment anyone builds the registration screen.
  - **The document was self-contradictory before this, which is the defect being fixed.** The operation's `description` already said *"Must be called from the same device that verified the OTP"*, its `201` was already documented as *"session issued (device bound)"*, and `registration_token_invalid` was already defined as covering *"expired/consumed/**wrong device**"* — while no schema carried a device. **The "wrong device" error the contract promised could never fire**, because the server had nothing to compare against. The server has required `device` since the endpoint was implemented; this entry makes the published contract tell the truth about it.
  - **Why `2.0.0-m1` and not `1.4.0-m1`.** Two independent reasons. (1) Semver: a required-field addition is a MAJOR change, and every previous bump here was additive. (2) **`1.4.0-m1` is burned.** It was briefly published on 2026-08-14 carrying a different change (`parentPhone` made optional on `UniversityRegistration`), then reverted ~15 minutes later without a changelog entry. If you pulled inside that window you hold a document labelled `1.4.0-m1` whose content **no longer exists** — `parentPhone` is REQUIRED on both tracks and always will be (adr-048 rejected). Reusing that number would put two different documents under one version string, so it is skipped permanently.
  - **Flutter partner — what to do.** Regenerate models. On the registration call, send the **same `device` you sent to `/auth/otp/verify`**: the `registrationToken` is device-bound, and a mismatch returns `registration_token_invalid`, meaning restart at `/auth/otp/request`. If you already hold a `1.4.0-m1` document, discard it.
  - `error-codes.md` and `realtime.md`: **unchanged.**
  - Breaking: **yes.**
- 2026-08-15 — **`POST /auth/recovery/start`'s description corrected: `recovery_unavailable` is still ONE shared code, and it stays shared (adr-053, adr-054)**. `info.version` **deliberately unchanged** at `1.3.0-m1` — see below. **Breaking: no**, and explicitly **NOT `BEHAVIOURAL`**: the server's behaviour is byte-for-byte what it was. **Nothing to do.**
  - **What changed: prose, on one `x-stability: draft` path, and nothing else.** The operation's description claimed `recovery_unavailable` covers *"BOTH unknown phone and no-parent-number-on-file"*. [[adr-053]] made the stored parent number mandatory on both tracks, so the second half of that sentence describes a state a registered account can no longer be in — the document was describing a case that cannot occur. No schema, no field, no requiredness, no response, no error code and no `x-stability` value moved. Regenerating produces **zero** client diff.
  - **The behaviour did NOT change, and that is the decision, not an omission.** `recovery_unavailable` remains ONE code covering an unknown phone and an unusable parent number, deliberately indistinguishable, because the whole point is to give an attacker less enumeration signal from the one endpoint in this API that confirms an account exists. adr-053 ruled the shared code stays shared even though one of its cases became unreachable. **Do not code a branch that tries to tell the two apart — there is nothing to tell apart, by design.**
  - **Why `info.version` is not bumped.** This is a prose fix to a `draft` path, and `draft` means the shape can change without the announcement ceremony `stable` paths get; there is no schema, behaviour or codegen signal for a version to carry. Recorded explicitly so a future reader sees a deliberate decision rather than a forgotten bump.
  - **Context, for the recovery ladder you will build against later.** This entry ships with spec-002 group 8, which implements adr-019's four rungs — `POST /auth/recovery/start` → `verify-parent` → `new-phone` → `confirm`. **All four remain `x-stability: draft` and are NOT safe to build against yet**: adr-054 leaves real questions open on this surface (the single-phone household, a parent who refuses to pass on the code, suspected compromise or hostile rebind, and whether the parent number should be possession-verified at registration at all). They will be announced here when they move.
  - `error-codes.md` and `realtime.md`: **unchanged.**
  - Breaking: **no.**
- 2026-08-13 — **The four unbuilt `/reference/*` pickers now declare the errors they could always return (adr-026, adr-028)**. `info.version` bumped `1.2.1-m1` → `1.3.0-m1`. **Breaking: no** — purely additive: no path added or removed, no schema changed, no field renamed, no requiredness moved, nothing narrowed. Your existing code keeps working untouched; it simply gains documentation for statuses the server could always have sent.
  - **Why this is `no` and explicitly NOT `BEHAVIOURAL`.** Nothing about the meaning, the returned set, or the conditions of return moves — the server's behaviour is byte-for-byte what it was. This entry fixes a **documentation defect**: `GET /reference/{schools,education-systems,universities,avatars}` declared `200` and nothing else, while the per-IP rate limiter has always been a path-prefix limiter on `/api/v1/reference` that covers them for free. The contract understated reality; it now matches. Recorded plainly so a future reader does not have to re-derive the classification. No operation carries `x-behaviour-changed`, and **no `x-stability` value changed** — all seven `/reference/*` paths were and remain `stable`.
  - **`429 rate_limited` added to all four** (`/reference/schools`, `/reference/education-systems`, `/reference/universities`, `/reference/avatars`), identical to the block the three geography pickers already carry. The 2026-07-30 entry below documented `429` on **three** `/reference/*` paths; these four were the omission. **Flutter partner:** handle `429` + `rate_limited` and honour `Retry-After` on these four exactly as you already do on `/reference/countries` — same code, same semantics, nothing new to learn.
  - **`400 validation_failed` and `404` added to `GET /reference/schools` only.** It is the only one of the four that takes parameters (`governorateId`, `cityId`, `q`, `cursor`, `limit`). A malformed `governorateId`/`cityId` is `400`; a well-formed but unrecognised one is `404 governorate_not_found` / `city_not_found` — the adr-028 §3 split already in force on `/reference/cities`. **The other three take no parameters and therefore deliberately declare no `404`:** an empty catalogue is a `200` with an empty array, not a not-found. That is designed behaviour, not a gap — do not code a 404 branch for them.
  - **`error-codes.md`: eight codes registered** — `governorate_not_found`, `city_not_found`, `school_not_found`, `university_not_found`, `faculty_not_found`, `study_year_not_found`, `education_system_not_found`, `avatar_not_found`. The first two are reachable **now** from `GET /reference/schools`; the rest are registered ahead of the registration and study-year validation surfaces that will return them, because adr-028 forbids inventing a code inline at the call site. `governorate_not_found`/`city_not_found` had been named in the registry's prose since 2026-07-30 but never given table rows — prose is not registration, so they are formally registered here. **Flutter partner:** you need AR/EN copy for the first two now; the other six will not appear on any `stable` path until their spec lands.
  - `realtime.md`: **unchanged.** No schema, no parameter, no `x-stability` and no existing response description was modified.
  - Breaking: **no.**

A patch bump, because infrastructure and metadata changes are patch-level by convention (adr-035); regenerating produces no client diff.

Every `stable` path in this document is now callable there, seeded with real reference data: 4 countries, 27 Egyptian governorates, 309 cities. **Flutter partner: you can stop building against the document alone and start integrating per feature against a live API.**

When a real domain lands, the URL changes and that change will itself be a changelog entry with its own version bump. **Do not hardcode this host** — put it in one place in your config. Auth is **not** live there yet (that is the next spec), so today the callable surface is the `/reference/*` pickers.

  - Breaking: **no.**
- 2026-08-11 — **Contract v1.2 — university terms: the catalog now returns LESS, and your codegen will not tell you (adr-036, adr-037, adr-038)**. `info.version` bumped `1.1.0-m1` → `1.2.0-m1`. **Breaking: BEHAVIOURAL** — read this entry even though regenerating produces almost no diff. Rationale in adr-038.
  - **THE CHANGE THAT MATTERS — `GET /catalog/subjects` keeps its exact schema and starts returning a strictly narrower set.** University content is now gated on **two independent conditions**: the subject's **term is released** for that student's cohort (the admin owns a per-cohort term calendar), **and** the student holds the relevant active entitlement. Nothing about the response *shape* changes, so a generated client compiles identically and silently receives fewer subjects. `GET /catalog/subjects/{subjectId}/tree` and `POST /quizzes` inherit the same gating. The three affected operations carry **`x-behaviour-changed: 1.2.0-m1`** in the YAML.
  - **`[]` IS NOW A NORMAL RESPONSE from `/catalog/subjects`** — this is the one most likely to be mis-shipped. A university student who registers **before their Term 1 start date** has an empty catalog and there is nothing wrong. **Flutter partner: your catalog screen needs a real empty state, and it must not be an error state.** An unreleased term is **absent**, not flagged — there is deliberately **no** terms endpoint, no `released: false`, and no way for the app to know an unreleased term exists. Do not build a "Term 2 unlocks soon" affordance; there is no data for one.
  - **A cached `subjectId` / `lectureId` can start returning `403 insufficient_scope`** without any contract change — the admin un-released that term for the cohort, or the entitlement lapsed. Handle it as a normal state. **No new error code** was added: `insufficient_scope` and `subscription_required` already cover every reachable case, and naming the unreleased state would contradict making it invisible.
  - **Additive (safe) — two nullable fields, on `StudentProfile.university` (`GET`/`PATCH /me`) and on every `/catalog/subjects` item:** `termId` (opaque UUID, nullable) and **`termNumber`** (integer `1`|`2`, nullable). Neither is `required`; both are `null` for all school-track resources, and on a university profile during the summer gap or when the cohort has no schedule. **University registration gains NO field** — the current term is derived from the calendar, never chosen, so `/auth/register` is untouched.
  - **Why `termNumber` exists and why you need it:** a year-long course is now **two subjects with the same `name`** (`Anatomy` term 1, `Anatomy` term 2), and both appear in one list. `termId` is opaque per adr-026 §7 — do **not** hardcode term ids and do **not** derive an order from them. **Order and group on `termNumber`.** Term *names* are never sent; render your own localized "Term 1" / "الترم الأول".
  - **New path — `GET /catalog/modules`, `x-stability: draft`, do not build against it yet.** The subject picker gains an admin-owned grouping overlay (`[{id, name, displayOrder, termId, termNumber, subjectIds}]`, `[]` for school students). A module is **navigation only** — it never scopes content or gates anything. **`GET /catalog/subjects` IS the permanent "All subjects" view** and stays `stable`: a subject can legitimately belong to zero modules, so a module-only picker would silently hide content. Marked `draft` because `subjectIds` may become embedded objects — build "All subjects" first.
  - `error-codes.md` and `realtime.md`: **unchanged.**
  - Breaking: **BEHAVIOURAL** (stable paths `/catalog/subjects`, `/catalog/subjects/{subjectId}/tree`, `POST /quizzes` — narrower result sets, unchanged schemas) **+ additive** (`termId`/`termNumber`, `GET /catalog/modules`). No field removed, no type narrowed, nothing new made required.
- 2026-07-30 — **Contract v1.1 — city fallback, optional school, per-resource not-found (adr-028)**. `info.version` bumped `1.0.0-m1` → `1.1.0-m1`. Registration is never blocked by reference data Deepveloper/the client hasn't supplied yet — see adr-028 for the full rationale. Breaking on `stable` paths; **both partners have work**:
  - **Flutter partner:** `SchoolRegistration` and `UniversityRegistration` now take `cityId` OR `cityName` (new field, free text, max 100) — at least one required, supplying both → `validation_failed`. `schoolId` is now optional for every school-track student, Egypt included (was Egypt-required). `schoolName` is removed from the contract entirely — drop it from request bodies, it is rejected as an unknown property server-side. `StudentProfile.geography.city` is now a union — `NamedRef` (has `id`) for a coded city, `{ name }` for free text — update the client model; the field itself is still always present. `StudentProfile.school.schoolName` is removed (`school.school` stays nullable, unchanged). Two new responses to handle: `404 country_not_found` on `GET /reference/countries/{countryCode}/governorates` and `GET /reference/cities`.
  - **UI/UX partner:** the accepted registration Figma has no path for a student whose city isn't in the coded list, and no way to skip the school picker — both are now valid, expected states. Registration needs: (1) a "my city isn't listed" free-text affordance on the city step, and (2) a skippable school step (Egypt included). Lands on top of the P0 gaps already in the 2026-07-06 design audit.
  - `country_not_found` added to `error-codes.md`, plus the new per-resource not-found convention (`country_not_found` now, `governorate_not_found`/`city_not_found`/… as those lookups land).
  - **`rate_limited` (429) added to `error-codes.md`**, and documented on all three `/reference/*` paths. These paths are unauthenticated by design (the registration screen needs them pre-auth), so they carry a per-IP rate limit; the contract promises a stable `code` on every non-2xx body, so the limiter's rejection needs one. It is deliberately **not** `otp_throttled` — that code is OTP-specific and would make the app show an OTP message for a geography lookup. **Flutter partner:** handle `429` + `rate_limited` on `/reference/*` and honour `Retry-After`.
  - **`GET /reference/countries/{countryCode}/governorates` gains a `400`** and `/reference/cities`' existing `400` is spelled out. The split is deliberate and worth internalising: a **malformed** `countryCode` (not ISO 3166-1 alpha-2 shape — `EGY`, `1`, empty) is `400 validation_failed`; a **well-formed but unrecognised** one (`XX`) is `404 country_not_found`. Codes are normalised case-insensitively, so `eg` is accepted as `EG`.
  - **Six corrupted schema descriptions fixed** (not a behaviour change — a defect in the v1 document itself). Unquoted YAML flow-mapping descriptions containing a comma were silently splitting into junk keys with `null` values, on `TokenPair.accessToken`, `SchoolRegistration.email`, `StudentProfile.badges`, `StudentProfile`'s and `PATCH /me`'s `email`, and `QuizQuestion.imageUrl`. Strict validators and code generators choke on these, so **if v1 codegen failed on any of those schemas, this is why** — regenerate against v1.1. No field, type, or requiredness changed; only the descriptions were repaired.
  - Breaking: yes (stable paths — `/auth/register` request bodies, `GET /me` response shape, two new 404s on `stable` reference paths).
