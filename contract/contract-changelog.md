# API contract changelog (partner-facing)

Every change to `openapi.yaml`, `error-codes.md`, or `realtime.md` gets a dated entry: **what changed, why, who's affected, breaking? (yes / no / BEHAVIOURAL)**. **Two partners watch this file: the Flutter mobile partner and the website partner** (adr-057) — so **every entry must state which consumers it affects** (mobile, web, or both). That is a standing rule, not a suggestion: an entry that concerns only one of them must not read as an announcement to both. In `openapi.yaml` the operations the website consumes carry `x-consumers`; absence of that key means mobile-only. Changes are announced at or before the weekly sync (Interfaces doc §1.5). Newest first.

> **`Breaking: BEHAVIOURAL` (adr-038)** — a third category, added 2026-08-11. The schema did not break (your build will succeed, your generated models are still correct) but the **meaning moved**: an endpoint returns a different set, or returns under different conditions, than it did before. **These are the dangerous ones** — a real break announces itself in your build output, a behavioural change never does. They are announced as loudly as a break and need the same acknowledgment. In `openapi.yaml` the affected operations carry `x-behaviour-changed: <version>`.

- 2026-09-11 — **The Anatomy Flashcards study surface arrives: two new `draft` operations, `GET /flashcards/lectures/{lectureId}/cards` (`getFlashcardsForLecture`) and `PUT /flashcards/cards/{flashcardId}/self-grade` (`setFlashcardSelfGrade`), plus an additive `hasFlashcards` on the university subject tree.** `info.version` bumped `3.11.1-m1` → **`3.12.0-m1`**. **Consumers affected: mobile.** **Breaking: no** — nothing existing moves. No path, field, type, requiredness, response code, error code, `x-stability` value or `x-behaviour-changed` stamp changes anywhere in this document; two paths, two component schemas, one tag and one additive field are **added**. `error-codes.md` is **unchanged** — both `403` codes have been registered since the first milestone and no flashcard-specific code is introduced. `realtime.md` is **unchanged** — flashcards have no realtime surface. The admin contract (`openapi-admin.yaml`, `error-codes-admin.md`, `contract-changelog-admin.md`) is **untouched**.
  - 🔴 **Both new paths are `x-stability: draft`. Do not build against them yet.** They flip to `stable` at ship, announced in a later entry — the `3.11.1-m1` pattern. `hasFlashcards` is on the already-`stable` `getSubjectTree`, and that field IS safe to read now.
  - **What the surface is.** `getFlashcardsForLecture` returns a cursor page of `FlashcardCard` — `{ id, front, back, imageUrl, selfGrade }` — for one lecture. `setFlashcardSelfGrade` records the student's latest `gotIt`/`again` for one card and answers `204`. `hasFlashcards` on each university tree lecture node says whether that lecture has any active cards, so the client knows whether to draw the affordance at all.
  - 🔴 **University track only, and a School client must not look for any of it.** `hasFlashcards` is **not** on `SchoolSubjectTree` and never will be; a direct call to either new path from a School caller is `403 insufficient_scope` with no flashcard-specific hint. There is deliberately no way to tell that refusal apart from "wrong cohort", "term not released for your cohort" or "that UUID names nothing" — same code, same message, permanently (adr-136). **Do not build an existence probe on these endpoints and do not report the identical bodies as a defect.**
  - 🔴 **The free preview shares the quiz allowance, and a short page is NOT the end of the list.** Without an active `flashcardSubscription`, each card not already shown **this week** consumes one unit of the **same 50/week counter quiz questions draw from** — one allowance across both surfaces, not 50 each. Re-delivery of an already-charged card is **free**, so paging back and forth never costs twice. When the remaining allowance cannot pay for a whole page, the server returns the prefix it can pay for with `hasMore: true` and a `nextCursor` at the first card you did NOT receive. **Branch on `hasMore`, never on `items.length`.**
  - 🔴 **Zero affordable is a `403 flashcard_subscription_required`, not an empty page.** An empty `items` array means the lecture genuinely has no active cards — a normal `200`. The two states are different and both are reachable. **`weekly_question_limit_reached` is NOT returned here**: it stays quiz-only, because the cure for flashcard exhaustion is the flashcard subscription rather than next week (adr-142 §5).
  - **A base subscription changes nothing.** The two subscriptions are independent, not a bundle (adr-004, adr-060): a `baseSubscription` holder without `flashcardSubscription` previews exactly like a free student, drawing the same shared counter — which their own quiz usage does not touch, because an unmetered plan writes no ledger row.
  - **`selfGrade` is latest-value-only and is yours alone.** A second grade replaces the first; there is no history, no score, no streak and no review schedule, and none is specified anywhere. Two students holding the same page see different `selfGrade` values. It exists so a "show me my *again* cards" filter survives a reinstall or a second device — **do not build spaced repetition on it.**
  - **`imageUrl` is `null` in every environment today and that is normal.** No card-image CDN origin is provisioned anywhere. Treat `null` as "no image", never as an error. When a value does appear it is content-addressed and immutable — a corrected image produces a **different** URL, never new bytes at the same one — so it is safe to cache forever, exactly like question images (`3.11.1-m1`).
  - **`pageSize`, not `limit`, and it maxes at 50.** These operations declare their own page-size parameter rather than reusing the shared `Limit` (max 100), because a page is charged per distinct card against a 50/week allowance and a 100-card page could spend a non-holder's entire week in one request. An out-of-range value is `400 validation_failed` on field `pageSize`, not a silent clamp.
  - Breaking: **no.**

Clients that already handle the nullable case need **no change**; clients that hard-coded "always null" must stop doing so.
  - **`imageUrl` stays null in an environment with no configured CDN origin — including staging today.** The origin is deployment configuration, not a contract value. Nothing is provisioned as of this version, so every environment still answers `null`. Do not treat a null as an error or as a missing image; it is the normal pre-provisioning answer and stays legal forever (spec-026, adr-141).

A value appears only when a later changelog entry announces it.
  - **Image URLs are immutable and safe to cache forever.** Keys are content-addressed (`sha256` of the bytes) and served `Cache-Control: public, max-age=31536000, immutable`. A curriculum correction produces a **different** URL, never new bytes at the same URL. Answer-option images are still not a contract surface.
  - Breaking: **no.**

The description's list carried a fifth item, "wrong track," while outcome Three separately and correctly assigned "the other track's id" to `400`. The two statements contradicted each other and the count was off by one.

- 2026-09-10 — 🔴 **`POST /quizzes` `mode: retakeWrong` now accepts an optional leaf id and NARROWS the pool to it — a request that reliably returned `400` now returns `201` or `403`.** `info.version` bumped `3.10.0-m1` → **`3.11.0-m1`**; `createQuiz` is re-stamped **`x-behaviour-changed: 3.11.0-m1`** (it was `2.3.0-m1`). **Consumers affected: mobile.** **Breaking: BEHAVIOURAL** — **the request and response schemas are untouched and a regenerated client is byte-identical**, because `lessonId` and `lectureId` already existed on this request body for `mode: normal`. What moved is which combinations are *legal* and what the server does with them. **This is the dangerous kind: your build will not tell you.** The ruling is adr-136 (the refusal shape) resting on adr-135 (the release gate on the retake pool).
  - **What became legal.** `{mode: retakeWrong, lessonId, length}` on the school track and `{mode: retakeWrong, lectureId, length}` on the university track. Exactly **one** leaf id, of the caller's own track — the pool is narrowed to that lesson or lecture. This is the terminal `replay` step of the Mistakes flow: tapping "Cell Structure — 8 mistakes" now builds a quiz from *that lesson's* wrong answers instead of the student's whole history.
  - 🔴 **Three outcomes, and you must branch on the STATUS, never on emptiness.** **(1)** Leaf **inside** the caller's closed set with no wrong answers in it → `201` with `questions: []`. That is a **normal** response — do not render it as an error. **(2)** Leaf **outside** the closed set → `403 insufficient_scope`. **(3)** Malformed shape → `400 validation_failed`, unchanged, same message.
  - 🔴 **The `403` body is BYTE-IDENTICAL to `mode: normal`'s out-of-scope refusal for the same caller, and its four causes are deliberately indistinguishable — permanently.** "Belongs to another school, education system or stage", "you are not enrolled in it", "that UUID names nothing at all" and "that university term is not released for your cohort" all produce the *same* code and the *same* message. This is a security property, not an omission (adr-136): response *shape* is a signal an attacker can script against without reading a field, which is why an out-of-scope leaf is refused rather than degraded to an empty `201`. **Do not attempt to tell the causes apart, do not report the identical bodies as a defect, and do not build a "does this lesson exist" probe on this endpoint.** The `201`-with-`[]` and the `403` are different states and both are reachable.
  - 🔴 **The question the operation's description used to call "not yet specified — do not infer either answer" is now ANSWERED, and that note is GONE (adr-135).** `retakeWrong`'s pool **is** release-gated; `favorites`' pool is **not**. So a university student's `retakeWrong` over an un-released term's lecture is refused as outcome (2), and that lecture's questions are absent from the *unscoped* retake pool too. **Re-releasing the term restores it unchanged — nothing is deleted** (adr-017 keeps every attempt forever; the gate filters what is drawable, not what is stored). School content is never release-gated (adr-073). There is still no release state on the wire and no way to distinguish the cause of a refusal, by design (adr-038 §3) — the same rule the `3.10.0-m1` entry states for shrinking `mistakeCount`s.
  - 🔴 **`mode: retakeWrong` with NO leaf id is unchanged and byte-identical.** If you send what you send today, you get what you get today. **`mode: favorites` is not changed in any way** — it accepts no leaf id, in any track, and asking for one is the same `400 validation_failed`, same message, it has always been. `quizType` also stays refused on **both** pool modes, same message: a retake follows what a student got wrong, not one revision session.
  - **Codegen impact: zero.** No path, schema, field, type, requiredness, response code, error code or `x-stability` value moves. The whole file diff is the version line, the `x-behaviour-changed` stamp, three request-property `description` strings and the operation's `description` prose. `error-codes.md`: **unchanged** — `validation_failed` (400) and `insufficient_scope` (403) have been registered since the first milestone and no retake-specific code is introduced. `realtime.md`: **unchanged** — quiz creation has no realtime surface. `openapi-admin.yaml`, `error-codes-admin.md`, `contract-changelog-admin.md`: **untouched.**
  - Breaking: **BEHAVIOURAL.**

- 2026-09-09 — **The Mistakes surface ships: two new read operations, `GET /me/mistakes` (`getMyMistakes`) and `GET /me/mistakes/subjects/{subjectId}` (`getMyMistakesForSubject`), both `x-stability: stable`.** `info.version` bumped `3.9.2-m1` → **`3.10.0-m1`**. **Consumers affected: mobile.** **Breaking: no** — nothing existing moves. No path, field, type, requiredness, response code, error code, `x-stability` value or `x-behaviour-changed` stamp changes anywhere in this document; two paths and two component schemas are **added**. `listSubjects` and `getSubjectTree` are **not edited at all**, in schema or in prose.
  - **What they are.** `getMyMistakes` returns a bare array of the subjects the caller **currently** has wrong answers in, each with a live `mistakeCount`. `getMyMistakesForSubject` returns the drill-down for one subject — school `units → chapters → lessons`, university `lectures` — as a `oneOf` discriminated on `track`, in the two new schemas `SchoolMistakesTree` and `UniversityMistakesTree`. Neither takes a scope parameter of any kind; the only client-supplied value on the whole surface is `subjectId`.
  - 🔴 **`mistakeCount` DECAYS and `mode: retakeWrong` does NOT — the two numbers are meant to disagree, and you must not reconcile them.** A `mistakeCount` counts a question only while the student's **most recent graded answer to it was wrong**. Answer it correctly in a later quiz and it leaves every `mistakeCount` immediately. The retake pool is a different rule — *ever wrong* — and that question **stays in it**. So a student can see `mistakeCount: 0` on a lesson and still be served that lesson's old question by `POST /quizzes` `mode: retakeWrong`. This is a deliberate ruling (adr-133), not a bug and not a race: **do not derive one from the other, do not "fix" the retake count from the tree, and do not report the difference as an inconsistency.** `POST /quizzes` is **not edited in this version** and its behaviour is unchanged.
  - **`[]` and the empty tree are NORMAL responses, and they are two different things.** `getMyMistakes` returns `[]` for a student with a clean record — a subject with zero current mistakes is **absent**, never present with `0`, which is why the overview's `mistakeCount` publishes `minimum: 1`. `getMyMistakesForSubject` returns `200` with `mistakeCount: 0` and an empty `units`/`lectures` for an **in-scope** subject the student has nothing outstanding in. **Clients MUST NOT render either as an error.**
  - **The tree is PRUNED and SUMMED, and it is not a clone of `getSubjectTree`.** A lesson or lecture appears only when its own `mistakeCount > 0`; a chapter only when it has such a lesson; a unit only when it has such a chapter. Every parent's count is the sum of its descendants'. There is therefore no dead branch to tap into. That is why these get their own schemas rather than reusing `SchoolSubjectTree` / `UniversitySubjectTree`, and why `UniversityMistakesTree` carries **no `quizTypes`** — a mistakes tree is a history view, not a quiz-build tree.
  - 🔴 **University students: a `mistakeCount` can SHRINK with no in-app explanation, and that is normal (adr-135).** University mistakes counts inherit the same release gate the catalogue and the retake pool already apply. When an admin **un-releases** a term for the caller's cohort, that term's subjects leave the caller's scope and their mistakes stop being counted — the node simply disappears under pruning, and `getMyMistakesForSubject` for that subject starts answering `403 insufficient_scope`. **Re-releasing restores both, unchanged; nothing is lost.** There is no release state on the wire and no way for the client to distinguish the cause, by design (adr-038 §3). **School content is never release-gated** (adr-073) and school counts never move for this reason.
  - **`403` on the subject route, and the trap inside it.** An out-of-scope `subjectId` is `403 insufficient_scope` — the identical answer `getSubjectTree` gives to the same membership question about the same id, so nothing new is learnable. 🔴 **A caller with zero mistakes anywhere still gets `403` for an out-of-scope subject** — not a `200` with an empty tree. The two are different states and both are reachable; branch on the status, never on emptiness. 🔴 **`getMyMistakes` also declares `403 insufficient_scope`, and it means something DIFFERENT from the subject route's `403` — do not collapse the two branches.** The overview takes no client-supplied id and refuses no id; its `insufficient_scope` says the caller has **no active enrolment** to scope a history against, which is reachable in ordinary use because a track transfer closes the old enrolment before the new one opens (adr-032). Render it as "your enrolment is between states" — it is not a membership refusal, not a reason to retry, and not a reason to log out. The subject route's `insufficient_scope` remains the membership answer about a `subjectId` you supplied, identical to `getSubjectTree`'s. The two operations' declared sets are now `200 · 401 · 403` on both, but only one of them can refuse an id, and that asymmetry in *meaning* is deliberate.
  - 🔴 **`insufficient_scope` is NOT the only `403` either route can return: both also answer `account_pending_deletion`, and both descriptions now say so.** That code has been reachable on **every** authenticated `/api/v1` endpoint except four (`GET /me`, `POST /me/deletion-request`, `DELETE /me/deletion-request`, `POST /auth/logout`) since **`3.3.0-m1`** (adr-114), the allowlist is an **exact four-route match and not a `/me` prefix**, and neither Mistakes route is on it — so a caller inside the 30-day deletion grace window is refused before either handler runs and before any `subjectId` is resolved. **This is a declaration, not a behaviour change**, and the same correction this file already made for the leaderboard in `3.5.1-m1`: no server behaviour moves, no new response status appears (`403` was already declared on both), no new error code enters the registry, and `info.version` is **not** re-bumped because `3.10.0-m1` has never been published — this corrects the entry above before it ships rather than superseding it. **Branch on `code`, not on the status:** if you already handle `account_pending_deletion` in the global interceptor as the `3.3.0-m1` entry instructed, you have nothing to do. **Zero codegen diff** — two `description` strings.
  - **No pagination on either path, deliberately.** Both sets are closed and bounded — by the caller's enrolment and by their own history — so the overview is a bare array like `listSubjects`, and the tree is a bare tree like `getSubjectTree`. Neither takes a cursor and neither will grow one.
  - **Codegen impact.** Two new operations and two new schemas; a regenerated client gains them and nothing else changes. Nothing became nullable, no field was added to or removed from an existing schema, and no requiredness moved.
  - `error-codes.md`: **unchanged** — `validation_failed` (400) and `insufficient_scope` (403) have both been registered since the first milestone and no new code is introduced by this surface; no row enters, leaves or moves. `realtime.md`: **unchanged** — mistakes have no realtime surface. `openapi-admin.yaml`, `error-codes-admin.md`, `contract-changelog-admin.md`: **untouched.**
  - Breaking: **no.**
