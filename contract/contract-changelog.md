# API contract changelog (partner-facing)

Every change to `openapi.yaml`, `error-codes.md`, or `realtime.md` gets a dated entry: **what changed, why, who's affected, breaking? (yes / no / BEHAVIOURAL)**. **Two partners watch this file: the Flutter mobile partner and the website partner** (adr-057) — so **every entry must state which consumers it affects** (mobile, web, or both). That is a standing rule, not a suggestion: an entry that concerns only one of them must not read as an announcement to both. In `openapi.yaml` the operations the website consumes carry `x-consumers`; absence of that key means mobile-only. Changes are announced at or before the weekly sync (Interfaces doc §1.5). Newest first.

> **`Breaking: BEHAVIOURAL` (adr-038)** — a third category, added 2026-08-11. The schema did not break (your build will succeed, your generated models are still correct) but the **meaning moved**: an endpoint returns a different set, or returns under different conditions, than it did before. **These are the dangerous ones** — a real break announces itself in your build output, a behavioural change never does. They are announced as loudly as a break and need the same acknowledgment. In `openapi.yaml` the affected operations carry `x-behaviour-changed: <version>`.

- 2026-09-03 — **`QuizSummary` stops reporting the student's standing: `totalPoints` and `level` are REMOVED, and `leveledUp`/`newBadge` become frozen events (adr-102)**. `info.version` bumped `2.3.0-m1` → **`3.0.0-m1`**. **Consumers affected: mobile.** **Breaking: yes** — two `required` fields leave the response of an `x-stability: stable` operation, so your generated models change and code that reads them stops compiling. **Regenerate, and read the "what to do" paragraph below before you delete anything.**
  - **The rule this entry is an instance of, and the sentence to keep** (adr-102 D1): **A field that describes an EVENT is frozen. A field that describes STATE is live.** Every field on every response in this document can be sorted by that one question, and the answer tells you whether it can move under you. `POST /quizzes/{quizId}/finish` was the one place the document got it backwards, and this entry is the correction.
  - **What changed, exactly.** `components.schemas.QuizSummary` loses `totalPoints` and `level` — from `properties` and from `required` both. **Retained and unchanged:** `quizId`, `score`, `totalQuestions`, `answeredCount`, `pointsAwarded`, `questions`. **Retained, with their meaning now stated:** `leveledUp` and `newBadge`, which are **frozen on the attempt at the moment the threshold was crossed** and never move again. `finishQuiz`'s `summary` and `description` say so. **No path, operation, error code or `x-stability` value moved anywhere in this document**, and `POST /quizzes/{quizId}/finish` stays `x-stability: stable`.
  - **This is a RELOCATION, not a lost capability.** The numbers are not gone from the API; they were never this operation's to report. `GET /me` (`getMyProfile`, `x-stability: stable`) already returns `points.school`, `points.university`, `points.total`, `level` and `badges`, and has since the first contract. **Nothing was added to `GET /me` for this** — the data the result screen needs is already there, in an operation you already call.
  - **Why the old shape was a defect rather than a convenience.** `totalPoints` and `level` were read **live** while `score`, `answeredCount` and `pointsAwarded` were **frozen on disk**, so `finishQuiz` was a half-frozen summary: two calls to the same idempotent operation returned **different bodies** if the student answered a question in a *different* quiz in between. The operation promises *"repeat calls return the same summary"*. It could not keep that promise while reporting a live total, and a published `stable` operation that contradicts itself is worse than a breaking change that fixes it.
  - **Why not freeze them instead.** Freezing `totalPoints` would put a points column in the `quiz` schema — a **second home for the student's points**, which adr-093 §5 forbids outright. It would also mint a permanently-inconsistent receipt (a total that will never again match reality) and show a 14-year-old a historical level number as if it were their level. **`leveledUp`/`newBadge` are frozen and `totalPoints`/`level` are removed for the same single reason:** the first pair describes an event, the second describes state.
  - **Design evidence, recorded so this is not re-litigated.** The live mobile result-screen frames — Figma nodes **`159:1964`** (LTR) and **`549:20247`** (RTL) — render **no absolute level number and no points total anywhere**. The level element is a **partial-fill meter**, and a meter needs live data by definition: `(points.total mod 500) / 500`, with `level` documented in this file as *"1–12, thresholds every 500 points; static, not configurable"*. **This change removes nothing the screen draws.**
  - **Flutter partner — what to do, in three steps.** (1) **Regenerate models** against `3.0.0-m1`; the compiler will point at every read of `summary.totalPoints` and `summary.level`. (2) **Where the result screen needs the student's current total or level, call `GET /me`** — same call you already make on app resume, no new endpoint, no new field. (3) **Keep reading `leveledUp` and `newBadge` from the summary, and read them as *"what happened in THIS quiz"*** — they are the celebration trigger, they are exact rather than reconstructed, and a later quiz can no longer switch them off. **Do not compute `leveledUp` yourself** by comparing two `GET /me` reads: that comparison is exactly the approximation this change deletes, and it is wrong whenever another quiz awarded points while this one was open.
  - **Secondary, and it is a SERVER change with no document change: a replayed `POST /quizzes/{quizId}/answers` now returns `pointsDelta: 0`** (adr-102 D2). This document has said *"0 or 1 (server-side award; **0 on retry replay** or free-plan edge)"* since `1.0.0-m1`; the server was returning the original award instead, and **the server is what moved.** `pointsDelta` reports **what THIS call awarded**, and a replay awards nothing. `openapi.yaml` is **not modified for this** and `submitAnswer` carries **no `x-behaviour-changed` stamp**, because the published text already described the corrected behaviour — there is no meaning here that moved on the wire, only an implementation that stopped disagreeing with it. **Nothing else about a replay changes:** the verdict, the correct option and the explanation flag are byte-identical to the original response, the answer still stands, and the point is still awarded exactly once. **If you display `pointsDelta` on a retried submit, expect `0`** — the awarded point is already reflected in `pointsAwarded` at finish and in `GET /me`.
  - **Why `3.0.0-m1` and not `2.4.0-m1`.** Removing `required` fields from a `stable` response is a MAJOR change under semver, on the same reading that took `POST /auth/register` to `2.0.0-m1` on 2026-08-16 for adding a required request field. **`Breaking: BEHAVIOURAL` was considered and rejected**: adr-038's third category is for a schema that did **not** break while the meaning moved, and this schema breaks — your build will tell you. It is not softened.
  - **`error-codes.md`: unchanged, and deliberately.** **No code enters or leaves the registry**, and no row's status or meaning moves — this change removes two fields from a `200` body and touches no failure path. `realtime.md`: **unchanged** — no realtime surface ever carried a quiz summary.
  - Breaking: **yes.**
- 2026-08-29 — **The catalog stops being entitlement-gated: `GET /catalog/subjects` returns MORE, and your codegen will not tell you (adr-091)**. `info.version` bumped `2.2.0-m1` → **`2.3.0-m1`**. **Consumers affected: mobile.** **Breaking: BEHAVIOURAL** — read this entry even though regenerating produces a **zero-byte** model diff. Rationale in adr-038; the classification is explained below.
  - **THE CHANGE THAT MATTERS — `GET /catalog/subjects` keeps its exact schema and starts returning a strictly WIDER set.** The `1.2.0-m1` note said university subjects were filtered by **TWO independent gates** — **Gate A** release and **Gate B** entitlement. **Gate B is removed from every catalog read.** The catalog is **browse-only**: a free student, school or university, now sees the complete catalog and tree they are permitted to browse. This read filters by **enrolment scope** and, for university, by **release** — and it **does not consult entitlement state at all**. `GET /catalog/subjects/{subjectId}/tree` and `GET /catalog/modules` follow it. The three `x-behaviour-changed` operations are **re-stamped `1.2.0-m1` → `2.3.0-m1`**: `listSubjects`, `getSubjectTree`, `createQuiz`.
  - **Gate B is not weakened; it is RELOCATED.** It moves off the read path and onto **quiz creation and question delivery**, where the product is actually consumed. adr-036 §7's demand that the gates be *independent* and adr-037 §1's proof that they read different inputs both survive intact — what changed is that only **one** of them is a read-path gate. **This is a paywall-placement decision, not a security relaxation.** Correct answers still never ship with questions; the bank is the product, and a subject's *name* is not. **Gate A — release — survives unchanged, stays UNIVERSITY-ONLY, and keeps its deliberate fail-open** (a cohort with no schedule row is released, adr-036 §7). School subjects are never release-gated (adr-073, untouched).
  - **`getSubjectTree`: a lapsed entitlement is no longer a cause of `403 insufficient_scope`.** The old note offered two causes — an un-released term, *or* *"the student's entitlement lapsed."* **The second clause is withdrawn.** `403` remains reachable, and remains a normal state for a client holding a cached `subjectId`: the subject fell outside the caller's **enrolment scope**, or the admin **un-released** its term for the cohort (adr-037 §3). **No error code was added, removed or re-meant.**
  - **`createQuiz`: the "same two gates as the catalog" sentence is no longer true and has been restated.** After adr-091 **the catalog has one gate and quiz creation has a different pair** — release **and** entitlement/quota. A university `lectureId` whose term is not released is still **not buildable** (`403 insufficient_scope`, no new code, an unreleased term is absent rather than nameable — adr-038 §7). What is newly stated in the contract is that **entitlement is enforced here rather than on the catalog read**: a student without an active `baseSubscription` may browse the whole catalog and build quizzes against the **free allowance**, and creation that would exceed it fails with `403 weekly_question_limit_reached` — the code this document has declared since `1.0.0-m1`, and which `error-codes.md` already classifies as *"Expected free-plan state, not a fault."*
  - **This resolves a contradiction the contract has carried since `1.2.0-m1`, in the contract's favour.** The document simultaneously said the catalog was entitlement-gated **and** that an unentitled student had a 50-questions-per-week allowance — but Gate B filtered that student's catalog to `[]`, which left the allowance with nothing to draw from. Both statements were published; they could not both hold. adr-065 §Correction found it by audit on 2026-08-19 and ruled it **contract-level, not implementational**; adr-091 rules it, and **the contract is the thing that moves.** Neither operation was ever implemented with Gate B, so this corrects a published intention, not a shipped behaviour.
  - **Why `BEHAVIOURAL` when the set only WIDENS.** adr-038's third category is about **meaning**, not direction. The returned set widening is the benign direction and nothing you have built can break on it — but *the conditions under which these operations return* have changed, and adr-038 requires that to be announced **as loudly as a break**, because a real break announces itself in your build output and a behavioural change never does. Recorded here rather than shipped as a quiet prose edit for exactly that reason. **`Breaking: no` was considered and rejected**: the 2026-08-19 precedent for `no` is prose that left server behaviour *byte-for-byte* unchanged, and this is not that — the gating rule itself moved.
  - **Flutter partner — what to do: nothing in code, one thing in your product model.** **Zero codegen diff**: no path, schema, field, requiredness, response, error code or `x-stability` value moved anywhere in this document. Regenerate if you like; the output is identical. **The one thing to change in your head:** an unentitled student is **no longer expected to see an empty catalog**. If you built an "empty catalog ⇒ probably unsubscribed" heuristic anywhere, delete it — `[]` still happens and is still a normal `200`, but now it means only *"no released subjects for this cohort yet"* (a university student registering before their Term 1 start date). **The paywall moment moves to quiz building**, where `403 weekly_question_limit_reached` is the signal. The app stays **purchase-silent** (adr-049 §3): a browsable catalog is **not** a paywall surface, and nothing here licenses a price, a paywall or a purchase link in the app.
  - **`GET /catalog/modules` is amended for consistency and is still `x-stability: draft`.** Its description said *"Same two gates as `GET /catalog/subjects`"* and its `subjectIds` said *"subjects that pass both gates"* — both were **cross-references to `listSubjects`' gating**, so leaving them would have published a contract that contradicted itself. They now read as the single release gate. **Recorded explicitly because it is the one edit outside adr-091 §6's named list of three operations:** the module overlay is unimplemented and `draft`, so this is a documentation-consistency fix with no consumer impact, and it carries **no `x-behaviour-changed`** stamp — the operation has never been safe to build against and its behaviour was never published as settled.
  - **`error-codes.md`: unchanged, deliberately.** No code enters or leaves the registry, and no row's status or meaning moves. `subscription_required` — *"Content requires `baseSubscription`"*, carrying **no track qualifier** — is **correct as written** and stays: there is one base subscription across both tracks (adr-091 §2). `weekly_question_limit_reached` and `insufficient_scope` are unchanged in value, status and meaning. `flashcard_subscription_required` remains university-only and additive on top of `baseSubscription` (adr-060).
  - **What is NOT specified here, so nobody infers it.** The free tier's mechanics — 50 **distinct** questions per week, consumed on **first server delivery**, **retries free**, reset **Monday 00:00 Africa/Cairo**, and the cap blocking **mid-quiz delivery** as well as creation — are **ruled in adr-091 §3 and owed by a later milestone's spec**, not published on the wire by this entry. No endpoint exposes the counter and none is promised. `realtime.md`: **unchanged**.
  - Breaking: **BEHAVIOURAL.**

- 2026-08-19 — **This contract now serves two build targets, and each operation names its consumers (adr-057)**. Ships in the same **`2.2.0-m1`** as the entry above; `info.version` moves once for both. **Consumers affected: mobile + web.** **Breaking: no** — nothing but metadata and prose was added, and explicitly **NOT `BEHAVIOURAL`**: the server's behaviour is byte-for-byte what it was. **Nothing to do**, for either partner.
  - **What changed.** The header comment and `info.description` now state that this document serves **two build targets** — the Flutter mobile app and the website — that operations are **mobile-consumed by default**, and that an operation that names its consumers via `x-consumers` names **all** of them. **`x-consumers` was added to exactly ten operations**, listed below: **nine carry `[mobile, web]`, and `POST /subscription-codes/redemptions` carries `[web]`** — it is web-only, per **adr-049 §4**, because the app never mentions voucher redemption. This changelog's own header line gained the second audience and the standing rule that **every entry must state which consumers it affects**; these two entries are the first to honour it. No path, schema, field, requiredness, response or error code moved.
  - **The rule, stated so you can apply it mechanically.** Operations are **mobile-consumed by default**. **Absence of `x-consumers` means mobile-only** — it does not mean "unknown", "not yet decided" or "not yet annotated". **When the key IS present it is the COMPLETE consumer set for that operation, and it REPLACES the mobile default rather than adding to it**: `[mobile, web]` means both build targets consume it, `[web]` means web only and the app does **not** consume it. A value that omits `mobile` is a deliberate statement, not an omission. **There is no second document and no operation has moved** (adr-057): the website is a second reader of this same contract, not a fork of it.
  - **`x-consumers` is documentation metadata and nothing else.** It records **who must be told when an operation changes** — that is its entire job. It is **not an authorization source, not a routing input, and not a stability signal.** It does not widen or narrow who may call an operation, it has no bearing on tokens, scopes or entitlements, and the server never reads it. This is the misreading that would cost the most, so it is stated plainly: if a line of reasoning about `x-consumers` arrives at a conclusion about *permissions*, the reasoning is wrong.
  - **The ten, by path.** **`[mobile, web]` — nine:** `POST /auth/otp/request`, `POST /auth/otp/verify`, `GET /reference/countries`, `GET /reference/countries/{countryCode}/governorates`, `GET /reference/cities`, `GET /reference/schools`, `GET /reference/education-systems`, `GET /reference/universities`, `GET /reference/avatars`. **`[web]` — one:** `POST /subscription-codes/redemptions`. **Those nine are `x-stability: stable`. `POST /subscription-codes/redemptions` is `draft` and stays `draft`** — being annotated with a consumer is **not** a promotion, and it is still not safe to build against. **No `x-stability` value changed anywhere in the document.**
  - **Flutter partner — no code to change, one build-target instruction.** An `x-`-prefixed key is a legal OpenAPI specification extension and generators ignore it: **zero codegen diff.** An operation carrying `[mobile, web]` has not changed for you in any behavioural sense — same shape, same semantics, same operation, now with a second reader recorded against it. One practical consequence falls on our side, not yours: a future change to any of these ten must be announced to two partners instead of one. **The one thing to act on: do not build voucher redemption into the app.** `POST /subscription-codes/redemptions` carries `[web]`, not `[mobile, web]` — it is a **web surface** (**adr-049 §4**), and its presence in this document is a record of the operation, not an instruction to implement it.
  - **Website partner — what this is.** These ten are the operations the website consumes today: phone verification, the seven `/reference/*` pickers, and subscription-code redemption. When one of them changes, the entry's `Consumers affected` line will name you — and when a line does not name you, that change is mobile-only and you can skip it. If the website begins consuming an operation that is not on this list, adding it is itself a contract change and gets its own entry here.
  - **No linter rule requires `x-consumers`, and none is planned.** An operation without the key is **correct**, not incomplete — mobile-only is the default, and annotating every mobile-only operation with `[mobile]` would add noise without adding information. Do not read an absent key as an oversight.
  - `error-codes.md` and `realtime.md`: **unchanged.**
  - Breaking: **no.**
- 2026-08-16 — **`POST /auth/recovery/new-phone` declares the `400 validation_failed` it has always returned**. `info.version` bumped `2.0.0-m1` → **`2.1.0-m1`**. **Breaking: no** — purely additive, and explicitly **NOT `BEHAVIOURAL`**: the server's behaviour is byte-for-byte what it was. **Nothing to do** unless you are building the recovery ladder, which is still `draft` and still not safe to build against.
  - **What changed.** One response added to one `x-stability: draft` operation: `400` + `validation_failed` when `newPhone` is missing or is not a valid E.164 number. No path, schema, field, requiredness, error code or `x-stability` value moved. `error-codes.md` and `realtime.md`: **unchanged** — `validation_failed` has been registered since the first contract.
  - **Why it was missing, and why the fix is a contract change rather than a code change.** `newPhone` is a `$ref: Phone` whose pattern the client is expected to enforce, so the operation was written as if a malformed value could not arrive. It can. The server has always answered `400 validation_failed`, because the two alternatives are both believable lies: `registration_token_invalid` would tell a student their still-valid rebind token is dead and cost them two proven recovery rungs, and `phone_already_registered` would claim the number belongs to someone else. The contract understated reality; it now matches.
  - **How it was found: Schemathesis, from outside, against a running server.** CI now fuzzes the `/auth/*` surface against this document and fails the build on any status a response returns that the contract does not declare (spec-002 group 11). It flagged this operation along with three others. **This is the gate working as intended** — the divergence had been known and written down in a code comment for a day, and the external check is what turned a comment into a change.
  - **The other three were fixed the opposite way, and the distinction is worth knowing.** `POST /auth/refresh` and `POST /auth/recovery/start` also emitted an undocumented `400` for a structurally malformed body (a JSON object where a string is declared, a non-object root, unparseable JSON, a missing `Content-Type`). On those two the absence of a `400` is a deliberate **security property**, not an omission — a field-level `400` tells an unauthenticated caller which half of a credential it got wrong, and on `recovery/start` it breaks the guarantee that a malformed number, an unknown number and an ineligible account are indistinguishable. So there the contract was right and the **code** was corrected: every unusable body now reaches the handler as an absent value and gets the published `401` / `404`. **No contract change on those two, and none is coming — do not code a `400` branch for `/auth/refresh` or `/auth/recovery/start`.**
  - Breaking: **no.**
